01 — Segment the source document

An agent divides the manuscript into logical sections. Segments may overlap and together must cover all content, reducing the chance that one very large reasoning pass glosses over localized flaws.

Google-published sequence; wording simplified. Internal prompts, models, scheduling heuristics, and inference scaling are not fully public. Official architecture announcement ↗

Why this architecture matters

  • Long documents contain cross-section dependencies that one-pass reviews miss.
  • Mathematical proofs and methodology need different reasoning budgets from introductions.
  • Parallel agents can inspect local targets while retaining full document context.
  • Synthesis reduces repeated or contradictory findings; it cannot guarantee perfect correctness.

Where the evidence stops

  • No public, fully reproducible source repository for the complete Deep Review runtime was identified.
  • Precise reviewer prompts and adaptive-compute policies are not published as a production specification.
  • Research results from the predecessor Paper Assistant Tool should not be treated as guarantees for all domains.
  • Review outputs remain advisory; domain experts own final decisions.

04 / Developer interface

API workflow & example requests

The published integration is asynchronous: ingest a document, create a review, poll a long-running operation, and fetch the completed review. Results include synthesized Markdown and location-anchored findings.

Enable the API

gcloud auth login
gcloud config set project YOUR_PROJECT_ID
gcloud services enable deepreview.googleapis.com
gcloud auth application-default login \
  --scopes=https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/drive.file

For production, use appropriately scoped workload credentials rather than a developer login.

Upload a PDF

curl -X POST \
  'https://deepreview.googleapis.com/upload/v1/documents?uploadType=media' \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  -H "x-goog-user-project: YOUR_PROJECT_ID" \
  -H 'Content-Type: application/pdf' \
  --data-binary '@architecture.pdf'

Parse the returned name (for example, documents/...) and persist it as your external document identifier.

Create an asynchronous review

curl -X POST \
  'https://deepreview.googleapis.com/v1/documents/DOCUMENT_ID/reviews' \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  -H "x-goog-user-project: YOUR_PROJECT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"runConfig":{"topology":"HIGH","userPrompt":"Review technical claims, logical consistency, security assumptions and supporting evidence."}}'

The request returns a long-running operation. Supported topologies are LOW, MID (default), HIGH and EXTRA_HIGH; model and geminiApiKey are also documented config fields.

Poll and retrieve

# OPERATION_NAME is the returned operation resource name:
GET https://deepreview.googleapis.com/v1/OPERATION_NAME

# Check error on every poll. Once done=true, the operation
# response contains the Review resource/name.

GET https://deepreview.googleapis.com/v1/documents/DOCUMENT_ID/reviews/REVIEW_ID

Persist operation identifiers, use exponential backoff on 429/5xx, include the supported requestId UUID for retry safety, and handle terminal operation errors.

Normalized findings model (illustrative)

{
  "reviewMarkdown": "Detailed synthesized report...",
  "anchoredComments": [{
    "commentId": "...",
    "severity": "MAJOR",
    "summary": "Claim needs stronger evidence",
    "bodyMarkdown": "Evidence and reasoning...",
    "suggestedEdit": "Proposed correction...",
    "location": {"pdf": {"pageNumber": 8}}
  }]
}

Example shape, not an actual service response. Official fields include CRITICAL / MAJOR / MINOR / SUGGESTION, PDF boxes/quote selectors, text line anchors and optional scholarly citation reports.

Authentication

OAuth 2.0, Google ADC and x-goog-user-project. Keep server-side secrets out of browser JavaScript.

Document lifecycle

Create, list, inspect, download, and delete documents. Track retention and cleanup from your own service.

BYOK inference

Optional Gemini API key in review config switches to caller-provided inference billing and bypasses the complimentary review quota.

Direct API use

Invoke the REST API from an authenticated script, notebook or client. Useful for testing, research workflows and small review batches.

Optional hosted wrapper

Run a lightweight API on Cloud Run, GKE, or another platform for async jobs, reporting, authentication and user-facing annotation views.

Key distinction

The external Google-hosted review engine stays separate from any application built around it. Wrapping the API does not make its proprietary internals self-hostable.

09 / Strategic options

Build vs buy: three credible paths

FASTEST PILOT

A · API-first

Integrate Deep Review directly through a narrow adapter. Best for experimentation on permitted documents and rapid comparison against human review.

Trade-off: Alpha availability, vendor dependency, limited custom orchestration.

RECOMMENDED

B · Hosted API with application wrapper

Build a simple submission and reporting layer around Deep Review for authenticated users, asynchronous status tracking, and review exports.

Trade-off: More engineering effort; stronger enterprise value and portability.

MOST CONTROL

C · Independent open-source-style alternative

Implement document splitting, reasoning-budget allocation, parallel reviewer agents and synthesis with independently chosen libraries and models, then benchmark quality.

Trade-off: Quality, inference efficiency and maintenance burden are yours.

Licensing nuance: Google's research description is public, but that does not grant rights to its proprietary service implementation. You can independently implement the high-level architectural ideas; do not equate that with reproducing identical internal behavior.

10 / Independent adoption study

Four-phase evaluation and integration plan

A provider-neutral, standalone plan for assessing Deep Review without requiring any specific organizational knowledge system or backend stack.

Phase 1 — Reproduce the documented API flow

Enable the API in a test Google Cloud project, upload permitted sample documents, launch reviews, poll operations and retrieve Markdown plus anchored findings. Gate: reproducible request/response behavior and clear operational limits.

Phase 2 — Independent quality evaluation

Create 20–30 representative documents with known issues; compare LOW/MID/HIGH against expert-labelled findings. Measure precision, recall, severity agreement, anchor alignment, cost, and latency. Gate: measurable advantages over a simple LLM baseline.

Phase 3 — Optional lightweight service

Build an isolated document-review API with access control, background jobs, configurable prompts, retry/backoff, result exports and an annotation interface. Gate: successful end-to-end demonstration with clear cost and failure states.

Phase 4 — Production feasibility decision

Review commercial terms, privacy, residency, Alpha risk, deletion semantics, data-processing approvals, and documented quotas. Decide whether to use the API for a controlled deployment or maintain it as a research/pilot tool. Gate: explicit acceptance of risks and independent provider contingency.

Suggested evaluation scorecard

  • Issue precision and recall versus human reviewers
  • Critical error miss rate and false-positive rate
  • Cross-section contradiction discovery
  • Accuracy of PDF/comment locations
  • Cost per confirmed actionable finding
  • Latency, failure rate and retry behavior

Scope of this research

Deep Review as an independent Google service: what it does, how its public architecture is described, how to call its API, and where its operational, licensing, accuracy and privacy limits matter. The sample integration is optional—not a recommendation to build a separate knowledge-management platform.

11 / Evidence & clarifications

FAQs and primary sources

Is Deep Review the same as Gemini Deep Research?

No. Deep Review focuses on analyzing and verifying supplied complex documents. Gemini Deep Research is primarily a multi-source research and synthesis workflow. Their objectives and exposed APIs should not be conflated.

Can I host Google's agents on GKE?

No public self-hostable distribution of the proprietary Deep Review engine has been announced. Your GKE service can invoke the hosted REST API and implement an independent private reviewer.

Can I use it with LangGraph?

Yes. LangGraph can orchestrate calls to the hosted REST API as one asynchronous task in a standalone document-review application.

Does it provide guaranteed financial, legal or regulatory accuracy?

No. It can surface inconsistencies and unsupported claims, but findings need authoritative grounding and appropriate expert assessment. It should not make unattended legal or regulatory sign-offs.

Can I sell a SaaS that uses it?

Integration is technically possible. Before offering white-label or resold services, independently verify Google's applicable service terms, resale conditions and customer-data requirements.

What is the difference between official facts and recommendations here?

Published API features, endpoint paths and limits are attributed to Google; diagrams, adoption plans and engineering patterns are independent illustrative analysis, not descriptions of Google’s proprietary deployment.
