Enterprise Ontology Visualizer — MVP 1 Codex Implementation Plan

Status: Implementation-ready specification
Product boundary: Standalone read-only ontology exploration, analytics, and mapping application. Do not introduce unrelated project names, components, or dependencies.
Stack: Existing RDF/OWL ingestion/conversion → FalkorDB → FastAPI + Pydantic → React + TypeScript + React Flow (@xyflow/react) + ELK.js + Zustand + TanStack Query. Canvas/WebGL is permitted for specialized very-large-graph modes.
Release scope: Everything described below is MVP 1, implemented via internal milestones.
Critical rule: Users cannot create, edit, delete, merge, approve, publish, or write back any ontology through this application. Remove OIDC integration for MVP 1.

1. Product vision and MVP 1 outcomes

The product turns very large enterprise ontologies into comprehensible, navigable, visually consistent, read-only experiences. A foundation ontology and multiple domain ontologies can be connected through imports, reused classes, subclass relations, shared properties, and cross-domain mappings.

Users can:

1. Browse ontology inventory, versions, imports, namespaces, domains, class families and coverage.
2. Explore hierarchies, multi-parent inheritance, class neighborhoods, properties, restrictions, equivalent/disjoint classes, imports and inferred relationships where available.
3. Expand and collapse branches lazily without materializing the complete graph in the browser.
4. Inspect all RDF details on demand: individuals, literal values, blank nodes, OWL restrictions, annotation statements, named graphs, source axioms and provenance.
5. Enter explicit dense-graph exploration with clustering, sampling, server-side tiles and Canvas/WebGL rendering; never use millions of React Flow DOM nodes.
6. Explore mapping views between foundation and domain ontologies, between two domains, and between concepts and properties; distinguish explicit mappings from derived candidate associations.
7. Access analytics views: structure, depth, breadth, reuse, orphan/disconnected concepts, import dependencies, fan-out hot spots, coverage, complexity, mapping coverage and quality signals.
8. Compare published snapshots in read-only diff mode. No merge/conflict-resolution/publish controls.
9. Search and filter classes, IRIs, synonyms/labels, namespaces, domains, entities and relationships.
10. Use breadcrumbs, focus mode, saved/shareable URL state, exportable reports/visualizations only, keyboard navigation and an accessible inspector.
11. See asserted and inferred semantics distinctly, with provenance, reasoner metadata and uncertainty/limitations clearly labeled.
12. Experience predictable latency, bounded requests, request cancellation, progressive results and graceful failure.

1.1 Explicit non-goals for MVP 1

• No authoring or editing of ontology entities, properties, classes, triples, restrictions, annotations or individuals, including raw RDF editing.
• No graph mutation API of any kind from the application; no FalkorDB CREATE, MERGE, SET, DELETE, REMOVE, schema/index-writing, imports, or data-changing administrative commands.
• No draft, autosave, undo/redo edits, patch journal, writeback, approval, publication, merge resolution, or user-initiated reasoning that changes canonical data. Navigation history is fine; data editing is not.
• No OIDC, OAuth, SSO, login screen, JWT/session handling or frontend bearer-token workflows in MVP 1. See §11 for production deployment restrictions while auth is deferred.
• No in-app upload/import/conversion of RDF files in MVP 1 unless the existing ingestion service independently owns it. Existing ingestion is an upstream prerequisite, not an editing surface.
• No replacing the canonical RDF/OWL source with an irreversible LPG-only model. Read-only fidelity and source-link verification remain mandatory.

1.2 Semantics of “mapping”

A mapping is information to discover, inspect, measure and visualize, not to author. Show evidence-backed relationships such as owl:equivalentClass, owl:equivalentProperty, rdfs:subClassOf, rdfs:subPropertyOf, owl:sameAs, skos:exactMatch, skos:closeMatch, imports, shared IRIs, and other mapping predicates configured for the deployment. The existence of a path or similar label does not prove equivalence. Candidate mappings generated by heuristics must be separately labeled as unverified suggestions and must not be persisted to FalkorDB by the visualizer.

2.1 Dependency assumptions

• FalkorDB is already populated by a separate RDF conversion pipeline.
• The canonical RDF/OWL artifacts remain independently versioned and retained.
• FalkorDB stores enough source identifiers, snapshot scope and provenance to support correct read-only projections; the implementation must inspect and verify this, not assume it.
• Choose one snapshot partition strategy after inspecting existing storage: graph per snapshot, or shared graph with mandatory snapshot-scoped filters.
• External reasoners, if present upstream, may supply precomputed inferred statements; the visualizer labels their provenance and never asserts or writes ontology changes.

2.2 Read-only enforcement at multiple layers

1. Configure a database principal limited to read operations and use it for all backend FalkorDB connections (where supported by the actual deployed FalkorDB security model).
2. Application query adapter exposes only named, parameterized, audited read query templates. Never expose arbitrary user-supplied Cypher.
3. No route, UI action, task worker, callback or connector used by this application can mutate ontology data or metadata.
4. Integration tests must verify there is no mutation route and that mutation attempts are rejected/blocked.
5. Do not rely solely on disabling edit buttons; make write operations impossible by architectural contract.
6. Read-only access to existing snapshot manifests, precomputed analytics and approved cache stores is allowed; writing derived cache entries is not writing ontology data. Maintain a strict separation between cache storage and FalkorDB.

3. Ontology identity, graph model and semantic fidelity

3.1 Required identity

Each response must identify ontologySetId, snapshotId, graphId (if applicable), entityIri, entityKind, sourceOntologyIri where known, and assertionStatus when the representation can be asserted/inferred. When blank nodes are used, preserve stable snapshot-local identities; do not claim that blank node IDs are globally stable across serializations or versions.

|RDF / OWL subject    |Expected view representation      |Notes                                        |
|---------------------|----------------------------------|---------------------------------------------|
|Ontology             |Catalog item / domain container   |IRI, version, imports, provenance            |
|Class                |Class node or collapsed group     |Full IRI is identifier; label is display-only|
|Object property      |Edge or property inspector        |Respect domain/range expressions             |
|Datatype property    |Inspector row; optional edge      |Literal datatype and language intact         |
|Individual           |Opt-in entity node / statement row|Paginated; do not render all by default      |
|Restriction / axiom  |Explainable semantic descriptor   |Display syntax, RDF source and provenance    |
|Blank node / RDF list|Detail expansion                  |Preserve RDF structure and context           |
|Named graph          |Filter/context marker             |Do not flatten away source graph identity    |
|Import relationship  |Ontology dependency edge          |Imported ontology may be unresolved          |
|Mapping assertion    |Typed mapping edge                |Predicate, confidence/evidence, source       |

Semantics caveats: owl:equivalentClass is not merely a manually asserted two-way rdfs:subClassOf; named class expressions may be complex; OWL class hierarchies need not be trees; inferred edges and mapping candidates require separate representations. Underlying conversion may lose constructs: in that case show an explicit mapping fidelity report and source RDF link, never silently invent an equivalent property-graph pattern.

3.2 Mapping predicate catalog

Keep a read-only, versioned configuration file (config/mapping-predicates.yaml) describing which RDF predicates represent which mapping type and how they display. Example categories: equivalent, exact, close, broader/narrower, inheritance, import, reuse, related, derived candidate. Configuration is a deployment artifact, not a user-editable ontology authoring feature.

3.3 Fidelity verification

On startup and in CI, validate representative fixtures against the existing converter: named graphs, subclass multiple inheritance, restrictions, equivalent classes, RDF lists, multilingual labels, shared IRIs, cycles, literal datatype/language, mapping predicates and inferred/asserted distinction. A fidelity report indicates preserved, source-only, lossy, or unsupported per construct. Never claim an automatic reversible RDF round trip unless the importer actually supports it; retaining the original canonical RDF is mandatory.

4.4 Cursor and query budgets

• Cursor is opaque, validated and bound to snapshot, projection, parent/focus, filters, sort order, page size and configuration version.
• Prefer indexed deterministic keyset pagination; offset pagination is acceptable only for small/static sources with proven consistency.
• Validate depth, fan-out, total row/page size, output bytes and allowed predicates on the server.
• Apply timeout, cancellation and backpressure to expensive graph requests.
• Report hasMore, truncation and sampling accurately. Unknown counts remain null, not zero.
• Cache keys include snapshot, query filters, projection version and semantic inference setting.

Create a restricted repository layer rather than interpolating UI-generated Cypher. First inspect the actual FalkorDB labels, relationship types, indexes, snapshot partitioning, ID storage and source graph provenance.

Required repository methods:

    async def get_class(self, snapshot_id: str, iri: str): ...
    async def get_children(self, snapshot_id: str, parent_iri: str, limit: int, cursor: str | None): ...
    async def get_ancestors(self, snapshot_id: str, iri: str, max_depth: int): ...
    async def get_relationships(self, snapshot_id: str, iri: str, predicates: list[str], limit: int): ...

    async def analytics(self, snapshot_id: str, metric_ids: list[str], filters: dict): ...
    async def get_statements(self, snapshot_id: str, filters: dict, cursor: str | None): ...

No execute_write, apply_patch, create_draft, persist_axiom, publish_snapshot or generalized execute_cypher API in the visualizer backend. If the connected FalkorDB instance does not support truly read-only credentials, deploy explicit query validation plus network isolation and clearly record the residual risk. Query validation is defense in depth, not a substitute for database-enforced permissions.

5.1 Hierarchy summaries

Compute direct child counts, optionally cached descendant counts, leaf counts, depth distributions and top-level roots from existing data. Prefer a separate derived analytics/cache store, or compute on demand; do not mutate FalkorDB ontology graphs. Full transitive closure can explode; use selective cached traversals and scoped queries.

5.2 Cycles and inference

Treat rdfs:subClassOf as a directed graph; guard against cycles and repeated ancestors. Support diamond inheritance without duplicating semantic entities. Display inferred relationships only if the persisted source or an already-available upstream inference result provides them; show reasoner and derivation provenance where available. No new reasoner implementation or ontology changes are required from the UI.

6. Lazy loading algorithm

6.1 Initial navigation

1. Load ontology-set/snapshot inventory and domain/ontology summaries.
2. User chooses an ontology/domain and a hierarchy root.
3. Fetch root and first page of direct children, optionally a small ancestor breadcrumb.
4. Show total/known direct counts, expandable indicators, and the exact active snapshot.
5. Render only bounded visible entities.

6.2 Expand

1. Mark branch loading, preserving existing nodes and coordinates.
2. Request children using snapshotId, parent IRI, filters and cursor.
3. Cancel or discard stale responses if focus, snapshot or filters changed.
4. Deduplicate by stable semantic node ID; keep multiple incoming edges for multiple inheritance.
5. Merge response into visible projection store; update continuation state and warning badges.
6. Apply incremental/stable ELK layout in a worker; preserve unaffected node positions where possible.
7. Allow Load more for high-fan-out branches rather than expanding all thousands automatically.

6.3 Collapse

Track visible paths/expansion ownership, not a simple global visited set. Collapsing one branch removes only nodes/edges not needed by another expanded branch, focus selection or pinned exploration context. Never delete persistent graph data. Maintain breadcrumbs and restored viewport on navigation.

6.4 Limits and progressive disclosure

Start with configurable engineering targets, measured in benchmarks: 50–150 visible React Flow nodes per typical view; first child page 25–50; no unbounded multi-hop traversal; pagination on every high-cardinality listing; Canvas/WebGL when clustering/large-scope views materially exceed DOM rendering budgets. These numbers are initial budgets, not guaranteed engine limits.

7. Visual design and UX

7.1 Core navigation views

• Ontology Overview: foundation/domain inventory, import arrows, shared vocabulary counts, domain dependencies, summary cards. Not a whole RDF dump.
• Hierarchy Explorer: collapsible rdfs:subClassOf branches, ancestor breadcrumb, multiple parent indicators, root picker, jump-to-class, fan-out summaries.
• Focus Explorer: selected class and a bounded neighborhood; predicate lenses (subclass, object properties, equivalence, restrictions, imports, cross-domain).
• Semantic Inspector: IRIs/prefixes/labels, type, source ontology/graph, axioms, restrictions, datatype/lang, provenance, outbound/inbound statements, inference badges. All details read-only.
• Dense Graph Explorer: clustered overview, semantic zoom, sampled edges, region drill-down, degree labels, optional Canvas/WebGL renderer; explicitly label aggregation and sample fraction.
• RDF Statement Explorer: cursor-paged/virtualized triple or quad table, datatype/language details, filters, source graph, read-only copy/export subject to deployment policy.
• Snapshot Comparison: side-by-side or unified read-only additions/removals/changed assertions, counts by predicate/class/domain, compare selectors and jump to contextual details.

8. Mapping explorer — mandatory MVP 1

Goal: Explain how foundation and domain ontologies relate, without allowing a user to assert or change mappings.

8.1 Mapping views

1. Foundation ↔ domain: select foundation ontology and one domain; display direct/indirect linkage, reused IRIs, imported vocabularies and explicit mapping statements.
2. Domain ↔ domain: select two domains; visualize mapped class families, cross-domain properties, shared entities and missing coverage.
3. Concept ↔ concept: inspect exact mapping predicate, source and target IRIs, named graph, version and source statement.
4. Mapping matrix: domains or namespaces on both axes; each cell shows count of explicitly asserted mappings and, separately, candidate suggestions (if available).
5. Coverage and gaps: number/percentage of in-scope classes with explicit mappings; clearly define denominator and count unresolved mappings separately.
6. Mapping search/filter: predicate family, source/target domain, namespace, asserted/derived, provenance, version, labels.

8.2 Mapping semantics and correctness

• Do not infer equivalence from string similarity. Similar labels can be used as candidates, clearly unverified.
• Model direction for subClassOf, broader, narrower, property range/domain and directional custom predicates; equivalence/exact-match are displayed as appropriate symmetry only when semantics justify it.
• Record edge provenance: source triple/quad, ontology set and snapshot, assertion type, graph IRI, optional confidence method.
• Avoid misleading aggregation: n mappings from a cluster must resolve to paginated source evidence.
• For unresolved targets, render a ghost/unresolved entry with an explanation; do not fabricate a target class.

8.3 Mapping APIs and example response

8.4 Mapping-specific tests

Test identical local names with different IRIs, explicit equivalence vs inferred/evidence-poor candidates, cross-version mapping changes, asymmetric mappings, multiple ontology memberships, source filtering, dangling targets, pagination, high-degree hubs, provenance and accurate coverage denominator.

9. Analytics — mandatory MVP 1

9.1 Dashboards

A. Ontology health and overview

• Ontology count, namespaces, total classes/object properties/datatype properties/individuals, statement count, named graphs, imports and versions.
• Breakdown by domain, ontology, predicate, entity kind, inferred/asserted and source.
• Source artifact coverage and ingestion fidelity warnings.

B. Class hierarchy analytics

• Roots, leaf classes, depth histogram, maximum/median depth, breadth and direct-subclass fan-out distribution.
• Multiple-inheritance count, classes with no meaningful hierarchy connection, connected components and cycles.
• Top high-degree nodes and class-family hotspots; percent of classes within chosen depth of a domain root.

C. Cross-domain dependencies and mapping coverage

• Imports between ontologies; reused vocabularies; cross-domain object-property links.
• Explicit mapping count, mapping type breakdown, source/target coverage, unmapped classes and unresolved targets.
• Domain-pair heatmap/matrix and dependency paths with traceable evidence.

D. Semantic quality signals (descriptive, not edits)

• Missing labels/descriptions (using configurable language/annotation rules).
• Duplicate display labels across distinct IRIs; deprecated references; unresolved imports; missing optional source metadata.
• Potential cycles and questionable mappings. Label heuristics as signals, not definitive ontology errors.
• Optional precomputed consistency/inference summaries from upstream reasoners only if available.

E. Version trends and read-only change analytics

• Compare two existing snapshots: class/property/statement changes, mapping coverage delta, import drift and changed class families.
• No draft, merge or publish actions.

9.2 Metrics contract

Each metric returns id, value, unit, definition, denominator (if a ratio), snapshotId, source, exact, approximationMethod (if relevant), computedAt, and possible warnings. Prevent misleading metrics: duplicates may be legitimate, ontology hierarchies may be cyclic, imported entities can be counted across multiple scopes, and percentages require explicit denominator rules.

9.3 Compute model

Prefer existing FalkorDB read queries for cheap aggregates; route expensive graph metrics through bounded asynchronous read-only computation and store results in a separate cache/analytics database. Mark freshness and snapshot version; never persist derived metrics as assertions into the source ontology graph. Index and memoize where beneficial; validate operational impact before requesting all-pairs paths or full graph traversals. Display progress/partial summaries for long-running analytics.

9.4 Visualizations

Use charts for histograms, stacked categorical breakdowns and trends; heatmaps for domain mapping coverage; dependency DAGs for ontology imports; bounded React Flow graphs for exploration. Offer click-through from charts to filtered graph/table evidence. Virtualize tables and provide CSV/JSON reports when explicitly enabled by deployment policy. Do not place thousands of chart bars or DOM nodes by default.

11. Security and deployment (OIDC deferred)

MVP 1 contains no OIDC or other built-in login/authentication flow. Remove identity providers, callback routes, token validation libraries, login buttons, account settings, RBAC/ABAC UI and authorization-specific user-role assumptions from the application implementation.

However, read-only is not synonymous with safe for public access. Ontologies may be commercially sensitive. For MVP 1:

1. Deploy only on a trusted private network or behind an independently managed enterprise gateway/VPN with access restrictions; do not expose an unprotected API publicly.
2. Allowlist CORS origins and apply network egress/ingress restrictions; use TLS at the ingress.
3. Keep FalkorDB credentials server-side, never in React bundles; choose least-privilege read-only DB access if supported.
4. Enforce read-only query templates, request validation, rate limiting, pagination limits and timeouts.
5. Avoid logging sensitive IRI contents and literal values by default; redact credentials and proprietary data.
6. Apply export/download limits and disable data exports by configuration when policies require it.
7. Ensure caches are private to the deployment and invalidated by immutable snapshot identity.
8. Design a future auth boundary as a separate follow-on work item; do not implement OIDC now.

Residual risk statement: Without user authentication there is no per-user authorization or auditable human identity. This MVP is appropriate only for an environment where perimeter access is already controlled and all authorized visitors may view the same dataset. If data needs per-domain or per-user restrictions, authenticated deployment is a prerequisite and is out of scope for this MVP 1.

18. Engineering cautions and decision log

1. Read-only is end-to-end, not only a frontend display mode. Enforce at the database connection and backend contract.
2. OIDC is intentionally deferred. Private/perimeter deployment is required until a future authenticated release.
3. Mappings are interpretive views, not authoring. Unverified suggestions must remain distinct from asserted RDF mapping semantics.
4. Analytics are descriptive. An observed cycle, duplicate label or low mapping coverage is not automatically an ontology error.
5. Canonical RDF stays authoritative. FalkorDB is a derived query graph and may not retain every OWL syntactic construct.
6. Projections are not raw database entities. UI grouping/clusters must not be confused with ontology assertions.
7. Query limits and semantic correctness take precedence over showing more nodes.
8. Snapshots are immutable reads. Never mix data, counts or cache entries from different snapshots.
9. Do not promise a live semantic reasoner unless an upstream maintained reasoner is available. Display precomputed inference transparently.
10. No unrelated project naming or code coupling.
