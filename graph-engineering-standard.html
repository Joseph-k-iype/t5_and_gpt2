Graph Engineering Standard for the FalkorDB estate

Today the platform is infrastructure: any team can point any source at any graph and model it however they like. This standard turns that into a governed estate — six pillars, a conformance ladder, and a catalogue that knows what exists.

If you run a business area

You are accountable for what's in your graphs

You will be named on a conformance report. What you need to know is which graphs belong to your domain, what data they hold, at what sensitivity, and whether the pipelines feeding them are governed or improvised.

Platform assumptions

These shape everything below. Confirm each against your deployed FalkorDB version before ratifying the standard — a wrong assumption here invalidates rules three sections down.

AssumptionWhat it means for the standardVerify
Query language is OpenCypher with FalkorDB extensions Every example in this document is Cypher. Procedure availability varies by version. CALL dbms.procedures()
A tenant is a graph key on an instance Isolation is at the graph level, not the schema level. There is no cross-graph query. Any federation happens in the application layer, and reference data must be replicated rather than joined. GRAPH.LIST
Index types: range, full-text, vector Range covers exact match and comparison; full-text brings stemming, stopwords and TF-IDF scoring; vector supports nearest-neighbour on euclidean or cosine. CALL db.indexes()
Constraint types: UNIQUE and MANDATORY, on nodes or relationships A unique constraint requires a supporting exact-match index to exist first. Creation is asynchronous: PENDING → UNDER CONSTRUCTION → OPERATIONAL or FAILED. CALL db.constraints()
Property values are scalars plus geospatial and temporal types String, boolean, 64-bit integer, 64-bit double, point, Date, Time, DateTime, Duration. null cannot be stored as a property value — absence is the only way to express it. Write a probe node
Nested structures are not a design target Do not build a model that depends on lists or maps as property values. Validate the behaviour of your version before relying on it. Version release notes
Operational warning · constraints

Adding a unique constraint to a graph that already contains duplicate values has, in at least some versions, caused instability during enforcement. Always run the duplicate-detection query (Appendix D) and resolve conflicts before issuing GRAPH.CONSTRAINT CREATE, and never introduce a new constraint directly into production without exercising it on a restored snapshot first.

Data engineeringData science 03 · Pillar one

Graph modelling standard

How we shape a graph. In a labelled property graph there is no class hierarchy to formalise — so the artefact is not an ontology, it's a registry, and it's concrete.

3.1 · The core artefact is a label registry

Three controlled lists, held in source control, reviewed like code:

Node labels

Each with a definition, an owner, a steward, and a property schema.

Relationship types

Each with permitted (source) → (target) label pairs and its own property schema.

Property keys

Each with a datatype, a classification, and a canonical definition.

Anything not in the registry is not permitted in an incubation or production graph. Sandbox graphs are exempt — that is what sandbox is for — but promotion out of sandbox requires registration of everything the graph contains.

3.2 · Property schema per label

Every registered label declares its property keys in three tiers. The tiers exist so that "we don't put risk scores on customers" is an enforceable statement rather than a preference.

TierMeaningEnforcement
RequiredMust be present on every node carrying this labelMANDATORY constraint
OptionalPermitted, defined, may be absentRegistry only
ProhibitedExplicitly disallowed — usually because it belongs on another label, or should be a nodeConformance check

3.3 · The property-versus-node decision rule

This is the single most consequential modelling decision, and the one teams get wrong most often. Apply the tests in order — the first "yes" wins and the attribute becomes a node.

Decide: property or node?

Answer for one attribute at a time
    #TestWhy it decides
    1Does it need its own relationships?A country string cannot participate in a trade-bloc hierarchy; a (:Country) node can.
    2Does it have an independent lifecycle?If it is created, versioned, expired or approved on a different clock from its parent, it is a node. A risk assessment is superseded; a customer is not.
    3Is it a shared controlled vocabulary?Reference data — country, currency, product code, business unit — becomes a node so the vocabulary has one authoritative definition and traversals can pivot through it.
    4Do you need to find all parents by this value, cheaply and often?Repeated global filters are a signal — though a range index is the cheaper first answer, and usually the right one.
    5Otherwise, it is a property.High-cardinality, single-use, non-relational, descriptive values stay as properties. Do not create a (:Timestamp) node.
    Counter-rule · do not over-nodify

    Every attribute promoted to a node adds a traversal hop to every query that touches it. If it fails all four tests, leaving it as a property is the correct answer — not a compromise, and not technical debt.

    3.4 · Relationship properties and reification

    Relationship properties are for qualifiers of that particular connection, never attributes of either endpoint.

    Permitted on edges
    • Temporal validity — validFrom, validTo
    • Strength or confidence — weight, confidence, matchScore
    • Provenance — the governance property set
    • Role or qualifier — role, ownershipPct
    Not permitted on edges
    • Attributes of the source or target node — put them on the node
    • Anything you will need to traverse from — an edge cannot have edges

    The reification rule. If a relationship needs its own relationships, or needs to be referenced by other parts of the graph, it must be reified into an intermediate node — typically an event or association node.

    Prefer reification early for anything that models an event, a transaction, or a decision. Retrofitting it later means rewriting every query that touches it.

    3.5 · Multi-label discipline

    FalkorDB permits multiple labels per node. Uncontrolled, this becomes the primary source of model drift — one team's subtype is another team's state flag, and neither is written down.

    • Every node carries exactly one primary type label — the registered entity type.
    • It may carry zero or more facet labels drawn from a controlled facet list declared against that primary type: Sanctioned, Deleted, Provisional.
    • Facets express state or classification, never a subtype with different properties. If the facet brings its own required properties, it is a distinct label or a related node.
    • Facets used as soft-delete or lifecycle markers must be declared in the registry — because every query author needs to know to exclude them.

    3.6 · Structural rules

    Direction is semantic

    Choose the direction that makes the edge read as a sentence, source to target. Never create both directions for the same fact — traversal is bidirectional in Cypher regardless.

    No duplicate parallel edges

    Not of the same type between the same pair, unless they carry distinguishing properties — usually temporal. If they do, document the disambiguating property in the registry.

    No orphan nodes in production

    A node with zero relationships is either reference data (declare it as such) or a defect. It appears in the conformance report either way.

    Supernode policy

    Any node exceeding the declared degree threshold — default 100,000 edges — must be reviewed. Remedies: partition by time bucket, introduce an intermediate grouping node, or demote the relationship to a property.

    Model depth for the query, not the whiteboard

    Every additional hop is a cost. Where a common query traverses a fixed three-hop path thousands of times a day, a materialised shortcut edge is legitimate — but it must be registered, and the pipeline that maintains it is a registered contract like any other. An undeclared shortcut edge is indistinguishable from a modelling error.

    Data engineeringBusiness & governancePlatform ops 04 · Pillar two

    Ingestion contracts

    This is the single control that converts "any data can go into the graph from any source" into a governed estate. Everything else in this document depends on it.

    The gate

    No data enters an incubation or production graph without a registered ingestion contract. The contract is a versioned artefact in source control, reviewed by the graph steward and the data owner, and referenced by ID from every node and relationship it creates.

    4.2 · Contract fields

    4.3 · Write-path rules

    Upsert, don't blind-create

    Default write pattern is MERGE on the identity key, then SET properties. Blind CREATE is permitted only for immutable event nodes.

    Idempotency is mandatory

    Re-running a contract over the same input must produce the same graph. This is what makes recovery possible — and recovery is the reason the rule exists.

    Contracts own their labels

    Two contracts writing the same property on the same label is a governance failure. Declare one authoritative and the other read-only, or split the property.

    Batch, don't write node-by-node

    Parameterised Cypher with UNWIND over a batch. Tune against your instance; start around 1,000–10,000 elements and measure.

    Index before bulk load, or index after — but decide deliberately

    Indexes accelerate the MERGE lookup but add write overhead on every insert. For a large initial load, loading first and indexing after is usually faster; for incremental upserts, the index must already exist.

    4.4 · The governance property set

    Every node and every relationship created by a contract carries these system-managed properties. The leading underscore marks them platform-owned and off-limits to application logic.

    PropertyTypePurposeProduction enforcement
    _contractIdstringWhich contract wrote thisMANDATORY
    _sourceSystemstringOriginating systemMANDATORY
    _sourceRecordIdstringKey in the source system, for round-trippingConformance report
    _pipelineVersionstringCode version that produced itConformance report
    _ingestedAtdatetimeWrite timestamp — drives freshness metricsMANDATORY
    _classificationstringSensitivity, inherited from the contractConformance report
    _validFrom / _validTodatetimeBusiness validity, where bitemporality is requiredConformance report

    Together these answer four questions that are otherwise unanswerable after the fact: where did this come from, when, by what code, and what must I delete if the source record is withdrawn.

    4.5 · Rejection rules

    A contract execution fails — loudly, not silently — when any of these hold. Rejected records go to a quarantine store with the failure reason. They do not go into the graph.

    It attempts to write an unregistered label, relationship type or property key.

    An identity key is null or empty, or collides with a different _sourceRecordId.

    A required property is absent for the label being written.

    A relationship endpoint label pair is not permitted for that relationship type.

    Payload volume deviates beyond the declared tolerance. A blown upstream join usually shows up as a 50× row count — and by the time anyone notices in the graph, the damage has propagated to every consumer.

    Data engineeringData sciencePlatform ops 05 · Pillar three

    Naming and identity

    Naming is cheap to standardise on day one and effectively impossible to standardise on day four hundred. Identity is what makes two graphs describe the same world.

    5.1 · Conventions

    ElementConventionExamples
    Graph key<env>.<domain>.<usecase>.v<n>prd.risk.kyc-network.v1
    dev.sandbox.shared
    Node labelPascalCase, singular nounCustomer · TradeAccount · RiskAssessment
    Facet labelPascalCase adjective or stateSanctioned · Deprecated
    Relationship typeUPPER_SNAKE_CASE, verb phraseHOLDS_ACCOUNT · REPORTS_TO · ISSUED_BY
    Property keycamelCaselegalName · openedAt · ownershipPct
    Governance property_camelCase — reserved prefix_ingestedAt · _contractId
    Index nameidx_<label>_<property>idx_customer_entityid
    Contract IDing.<domain>.<source>.v<n>ing.kyc.corereg.v2

    Singular labels always

    Customer, never Customers. The label describes one node, not the set.

    No abbreviations

    Unless the abbreviation is the enterprise-standard term. KYC, LEI, ISIN are fine; Cust, Txn, Acct are not.

    Verbs for edges, nouns for nodes

    OWNS, not OWNER. If you want a noun relationship type, you probably need reification.

    No type suffixes on keys

    openedAt, not openedAtDate. The registry declares the type; the key names the thing.

    Booleans read as assertions

    isActive, hasConsent — not active, consentFlag.

    Underscore is reserved

    The _ prefix belongs to the platform. Application properties must never use it.

      5.3 · Property keys are the real drift risk

      Labels and relationship types are visible in every query and get reviewed. Property keys proliferate quietly. customerName, custName, name, legalName, full_name across five tenants is the normal outcome of having no standard — not a worst case.

      Control one

      A shared property key dictionary

      Held in the catalogue. Before a contract introduces a new key it must check the dictionary and either reuse the existing key or justify a new one. The dictionary holds: key, canonical definition, datatype, classification, and the labels it appears on.

      Control two

      A weekly drift report

      Lists property keys observed in graphs but absent from the dictionary, ranked by node count. Anything above threshold goes on the steward's queue. Ranking by node count is what stops the report becoming noise.

      5.4 · Identity strategy

      Every registered label declares exactly one identity strategy. There are two permitted patterns, and the choice between them is about how many systems get to describe the entity.

      Pattern A

      Namespaced natural key

      Use when a single authoritative source system owns the entity and its key is stable.

      Cheap, transparent, debuggable, and requires no crosswalk. It breaks if the source re-keys, or if a second source starts describing the same entity.

      Pattern B

      Minted enterprise identifier

      Use when multiple sources describe the same entity, or when the entity must survive source-system replacement.

      The mint is issued once by the identity service and never changes. Every source key that resolves to it is recorded in a crosswalk: (:Customer)-[:IDENTIFIED_BY]->(:Identifier {system, value, confidence, resolvedAt}).

      Composite keys

      Derive a deterministic hash of the normalised, ordered components rather than concatenating raw values — and record the hash recipe in the registry, because it is impossible to reverse-engineer later and you will need it the first time a key doesn't match.

      Identity rules

      • entityId is mandatory on every node in incubation and production graphs. It is the only property guaranteed present everywhere.
      • A UNIQUE constraint on entityId per label at production tier. Create the supporting range index first, resolve duplicates first, and verify with db.constraints() that it reached OPERATIONAL rather than FAILED.
      • Never key on a mutable business attribute. Not email, not name, not an account number that gets recycled.
      • Never key on the internal node ID. It is not stable across restore, rebuild, or graph copy.
      • Entity resolution is a pipeline concern, not a query concern. Fuzzy matching happens upstream and produces either a mint assignment or an explicit (:Customer)-[:SAME_AS {confidence, method, resolvedAt}]->(:Customer) edge. Never let probabilistic matches silently collapse two nodes into one — the SAME_AS edge preserves the evidence and can be reversed.
      • Cross-tenant identity is declared, not enforced. Since graphs cannot be joined, two tenants using the same entityId for the same real-world entity is a convention held together by the catalogue. Registering that both align to the same canonical concept is what makes future federation possible.

      6.3 · Expiry and reaping

      Dead PoCs are the main cause of sandbox sprawl. This sequence is deliberately asymmetric: renewal is easy, deletion is slow. The goal is a true inventory, not friction.

      1. Day 0

        Created

        Graph created with an owner and a TTL recorded in the catalogue. No owner, no graph.

      2. TTL − 14d

        Notified

        Owner notified. Renewal is a one-click acknowledgement with a stated reason.

      3. TTL

        Frozen

        Reads permitted, writes blocked, marked Dormant in the catalogue.

      4. TTL + 30d

        Archived

        Snapshot exported to cold storage; the graph key is deleted.

      5. + 90d

        Gone

        Snapshot deleted. This is the last point at which anything is recoverable.

      Inactivity trigger

      Runs in parallel with the TTL clock: no queries for 45 days moves a graph into the same sequence regardless of how much TTL remains. A graph nobody queries is not a graph anybody needs.

      6.4 · Shared sandbox rules

      The shared sandbox is the most valuable thing on the platform and the easiest to ruin. Four rules keep it usable.

      One graph key per user or PoC

      Named dev.sandbox.<user-or-poc>. Shared graph keys become nobody's graph key.

      Per-graph size cap

      Breaching the cap is a signal the PoC should be promoted, not grown in place.

      No sensitive production data

      Nothing above the agreed classification threshold in the shared sandbox. Confidential or restricted data requires a dedicated incubation tenant with proper access controls — even for a PoC, even for a week.

      No backup, stated up front

      Sandbox graphs are not backed up, and that is said at creation time rather than discovered at loss time.

      Platform opsData engineeringBusiness & governance 07 · Pillar five

      Observability and lineage

      A standard nobody measures is a preference. Everything here rolls up into one number per graph, published weekly, next to the owner's name.

      7.1 · What we measure

      Daily, per graph

      Structural

      • Node count by label; relationship count by type
      • Distinct property keys, and key count by label
      • Graph memory usage
      • Index inventory and type per label/property
      • Constraint inventory and status — anything not OPERATIONAL is an alert
      • Degree distribution; count over the supernode threshold
      • Orphan node count by label
      Per contract

      Freshness & lineage

      • max(_ingestedAt) per _contractId against declared cadence → staleness alert
      • Records written, updated, rejected per run
      • Rejection reasons, grouped
      • Run duration and its trend
      • Volume deviation against the trailing baseline
      Continuous

      Query

      • Latency percentiles — p50 / p95 / p99 per graph
      • Slow query log, ranked by total time, not worst single execution
      • Query count per graph — feeds the inactivity trigger
      • Full scans on labels that have an index available

      That last one is usually a query-authoring defect and occasionally a missing index. Both are worth knowing; neither shows up anywhere else.

      7.2 · The conformance score

      One number per graph, published weekly, so the standard is measurable rather than aspirational. Move the sliders to see how a real tenant would score — the weights are the ones proposed for ratification.

      7.3 · What lineage actually answers

      Node-level provenance gives you record lineage. Contract-level metadata gives you dataset lineage. Together they answer the three questions that arrive as incidents, not as requests.

      "We're decommissioning this source system — what breaks?"

      Traverse SourceSystem ← READS_FROM ← IngestionContract → POPULATES → LabelDef → DECLARED_BY → Tenant. You get every affected graph, its tier, and its owning team.

      "This customer record is wrong — where did it come from?"

      Read _sourceSystem and _sourceRecordId straight off the node. No archaeology, no guessing which of four pipelines wrote it.

      "That source had a bad batch on Tuesday — what do I reprocess?"

      Filter on _contractId and _ingestedAt, then re-run the idempotent contract. This is the payoff for the idempotency rule.

      Everyone 08 · Pillar six

      The knowledge catalogue, as a meta-graph

      Build the catalogue of the graph estate in a graph. Every question about the estate is inherently relational — which labels does this team own, which contracts break if this source retires, which tenants share this concept — and those are exactly the queries a graph answers well.

      Dedicated graph key

      prd.platform.catalog.v1 — a production tenant like any other, held to this standard like any other. If the standard is not good enough for the catalogue, it is not good enough.

      8.1 · Two layers, and the gap between them

      Every catalogue node carries an _origin property with one of two values. The whole design rests on keeping them separate.

      _origin: observed

      What actually exists

      Discovered automatically by introspecting every graph key. Facts, not intentions. Refreshed daily; anything unseen for 30 consecutive days is marked Dormant.

      _origin: declared

      What we said would exist

      Registered by humans: definitions, ownership, classification, intent, TTL. Sourced from the YAML registry and contract files on merge. Source control is the system of record; the catalogue is the queryable projection.

      Drift is the set difference

      Observed but not declared is unregistered data. Declared but not observed is either a stale registration or a broken pipeline. Both are actionable, and both are trivial Cypher once the two layers coexist in one graph.

      Never edit the declared layer in the graph directly. The moment the catalogue and source control diverge, you will trust neither, and the catalogue becomes another thing people work around.

      8.2 · The meta-graph model

      The spine runs left to right: who owns it → which tenant → what is modelled → what it means. Ingestion contracts enter from below, connecting source systems to the labels they populate.

      Also in the catalogue, omitted from the diagram to keep the spine readable: IndexDef and ConstraintDef (attached to LabelDef, carrying type, target and current status).

      The piece that makes federation possible

      CanonicalConcept. Two tenants both have a Customer label; both align to concept:party.customer. Now you can answer "who else models this concept" without either team having to know the other exists.

      8.3 · Populating the observed layer

      A daily job iterates every graph key, calls the introspection procedures (db.labels(), db.relationshipTypes(), db.propertyKeys(), db.indexes(), db.constraints()) plus counts, then upserts the definition nodes with _origin: 'observed', firstSeenAt and lastSeenAt.

      A trap worth knowing about

      Label and property-key introspection tells you what exists, not what co-occurs. To learn which property keys appear on which label you must sample per label — and a sample is a sample, so record the sample size alongside the result.

      Business & governancePlatform opsData engineering 10 · Adoption

      The conformance ladder

      Adopt in stages rather than declaring everything non-compliant on day one. A standard that makes every existing team a violator on publication day gets ignored on publication day.

      L0

      Inventoried

      The graph exists in the catalogue with a named owner and a TTL. Nothing else. From a standing start this alone is a large improvement — and it is all the shared sandbox ever needs.

      Sandbox minimum
      L1

      Described

      Labels, relationship types and property keys registered; classification agreed. You can now answer what is in it without opening a query console.

      L2

      Governed

      Every source has an ingestion contract; governance properties present on every node and edge; identity strategy declared per label.

      Incubation minimum
      L3

      Enforced

      Constraints operational; conformance score above threshold; freshness monitored; retention implemented and exercised.

      Production, within grace period

      Suggested sequence

      Five overlapping phases. The ordering matters more than the dates: measurement precedes policy, pilots precede rollout, and enforcement comes last.

      1. Weeks 1–3

        Measure before you govern

        Stand up the catalogue graph and the observed-layer introspection job. Do this before writing any policy — you cannot govern an estate you have not measured, and the first inventory usually reframes the priorities.

      2. Weeks 3–6

        Ratify naming and the modelling rule

        Agree the conventions and the property-versus-node rule. Publish the property key dictionary seeded from what is already observed, so it starts as a description rather than a wish.

      3. Weeks 5–10

        Build the templates, pilot with two teams

        Registry and contract templates. Onboard two willing teams and fix the templates based on what they actually hit.

      4. Weeks 8–14

        Backfill and publish

        Backfill registrations for existing production tenants. Publish the first conformance report — visibility, not enforcement.

      5. Weeks 12–20

        Turn on enforcement

        Constraints, rejection rules, lifecycle automation. Enforce on new tenants first, then migrate existing ones on a published schedule.

      Appendix E · Open decisions for the review forum

      Seven decisions this draft does not make. Each one is cheap now and expensive later — which is precisely why they are listed rather than assumed.

      1. Property key case

        camelCase is assumed throughout. If the wider enterprise standard is snake_case, change it now, before anything is registered.

      2. Bitemporality

        Is _validFrom/_validTo mandatory across the estate, or opt-in per label? Retrofitting it is expensive.

      3. Soft delete

        Facet label, validTo, or hard delete? Pick one. A mixed estate is unqueryable — every consumer has to know which convention each tenant chose.

      4. Reference data

        One shared reference graph replicated per tenant, or reference nodes duplicated per tenant? Since graphs cannot be joined, replication is likely the only option — agree the sync mechanism and who owns it.

      5. Vector embeddings

        If GraphRAG is in scope, embeddings need their own standard: which property key, where the model version is recorded, which index type and similarity function, and the re-embedding policy on model upgrade. An estate with three embedding conventions has none.

      6. Supernode threshold

        100,000 is a placeholder. Set it from your actual latency measurements, not from this document.

      7. Conformance thresholds and grace periods

        What score is required at production tier, and by when? Without a number and a date, the ladder is decoration.

      Next step

      Take this to the architecture forum with Appendix E answered

      Seven decisions, one hour. Everything else in this document can be adopted incrementally — those seven cannot, because each one is baked into the first registration that follows it.
